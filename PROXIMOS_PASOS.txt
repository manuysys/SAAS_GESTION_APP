# 1. OBJETIVO

Preparar el producto para que tres empresas piloto puedan utilizarlo sin que el fundador tenga que modificar directamente la base de datos.

La definición de éxito es:

Una empresa puede registrarse, configurar su negocio, invitar empleados, cargar clientes, gestionar órdenes, enviar presupuestos, permitir que el cliente los apruebe, registrar pagos y utilizar la aplicación móvil.

Toda la operativa debe realizarse desde las interfaces del producto.

No empezar una reescritura.

No agregar funcionalidades que no contribuyan a este objetivo.

No sacrificar seguridad por velocidad.

# 2. IDENTIDAD

Empresa: ARVOKTA.

Producto: DOVEXO (aprobado como nombre comercial el 2026-11-10; dominio y registro marcario pendientes).

ARREGLO es una denominación histórica utilizada por una primera implementación y NO es el nombre comercial actual.

DOVEXO fue un candidato y quedó aprobado por decisión del fundador. Antes de usarlo en documentos legales o en Google Play falta verificar disponibilidad marcaria y registrar el dominio.

Centralizar el nombre del producto, logotipo, colores y metadatos comerciales.

No hacer reemplazos masivos que puedan romper rutas, APIs o identificadores internos.

Preparar la aplicación para cambiar de identidad sin afectar su funcionamiento.

# 3. DECISIONES DEL FUNDADOR

Aplicar estas decisiones como valores predeterminados del proyecto:

- Distribución Android: Google Play, comenzando por prueba interna.
- Email transaccional: Resend.
- Cobros iniciales del SaaS: transferencia bancaria manual.
- Pasarela de pagos: Mercado Pago posteriormente.
- WhatsApp: integración posterior, no bloquear el piloto por falta de credenciales.
- Empresas piloto: tres negocios inicialmente, preferentemente del mismo rubro.
- Mercado inicial: servicios técnicos a domicilio.
- Arquitectura: conservar la implementación existente.

Si falta una cuenta, credencial o permiso externo, implementar la parte técnica posible y documentar el bloqueo.

Investigar la arquitectura actual de notificaciones y autenticación.

Integrar Resend en el backend FastAPI.

Documentación oficial:
https://resend.com/docs

Referencias de integración:
https://resend.com/fastapi
https://resend.com/python

Crear un módulo de email reutilizable.

No llamar directamente a Resend desde distintos endpoints con código duplicado.

Implementar plantillas para:

- Invitaciones de empleados.
- Acceso al portal de clientes.
- Recuperación de contraseña.
- Verificación de email.
- Notificaciones transaccionales necesarias.

Requisitos:

1. Utilizar RESEND_API_KEY como secreto.
2. No exponer la clave al frontend.
3. Configurar el remitente desde variables de entorno.
4. Utilizar plantillas HTML y texto plano.
5. Registrar identificadores de proveedor.
6. Registrar estados de envío.
7. Manejar errores.
8. Implementar reintentos seguros.
9. Usar idempotencia donde corresponda.
10. No duplicar emails por reintentos de operaciones.
11. Diferenciar email solicitado, aceptado por el proveedor y entregado.
12. Registrar fallos sin almacenar secretos.

Preparar configuración de dominio.

Variables de entorno de ejemplo:

RESEND_API_KEY=
EMAIL_FROM=
APP_PUBLIC_URL=

No inventar valores reales.

El dominio debe contar con configuración DNS adecuada.

Comprobar SPF, DKIM y DMARC.

Mientras no exista un dominio verificado, permitir pruebas controladas, pero no considerar completa la entrega productiva.

# 5. PRIORIDAD P0: INVITACIÓN DE TÉCNICOS

Esta funcionalidad es fundamental para el autoservicio.

Actualmente los técnicos de demostración se crearon mediante SQL.

Eliminar esa dependencia de procesos manuales.

## Flujo

1. El dueño ingresa al panel.
2. Abre la sección Equipo.
3. Selecciona Invitar técnico.
4. Completa nombre y correo.
5. Selecciona rol permitido.
6. Confirma.
7. El backend crea una invitación.
8. Se envía un correo.
9. El empleado abre el enlace.
10. Acepta la invitación.
11. Inicia sesión o crea su cuenta.
12. Se crea la membresía en la empresa.
13. Aparece automáticamente en el equipo.

## Requisitos técnicos

Crear o reutilizar una entidad de invitación.

Campos mínimos:

- id.
- tenant_id.
- email_normalized.
- role.
- invited_by.
- token_hash.
- expires_at.
- accepted_at.
- revoked_at.
- created_at.

Usar tokens aleatorios de alta entropía.

Guardar hashes, nunca tokens en texto plano.

Establecer expiración configurable; usar siete días como valor inicial razonable.

Permitir:

- Reenviar invitación.
- Revocar.
- Consultar estado.
- Volver a invitar.
- Detectar invitaciones vencidas.
- Detectar correos incorrectos.

Una invitación solo se puede utilizar una vez.

El email verificado de la persona que acepta debe coincidir con el destinatario de la invitación.

Si el usuario ya tiene cuenta, permitir asociarlo a otra empresa sin duplicar su identidad.

No permitir que un técnico pueda invitar propietarios ni administradores.

La empresa controla qué roles puede asignar.

Validar los límites de usuarios y técnicos antes de invitar.

Evitar race conditions cuando dos administradores intentan ocupar el último asiento simultáneamente.

## Frontend

Crear una sección de administración del equipo.

Mostrar:

- Nombre.
- Email.
- Rol.
- Estado.
- Fecha de invitación.
- Último acceso, si existe.

Estados:

- Activo.
- Invitación pendiente.
- Vencida.
- Revocada.

Agregar formulario de invitación, reenvío y revocación.

Utilizar mensajes claros.

No mostrar errores internos del backend al usuario.

# 6. PRIORIDAD P0: ACCESO AL PORTAL DEL CLIENTE

Actualmente el magic link funciona en la demo mediante dev_token, pero no existe entrega real de acceso.

Eliminar completamente dev_token de producción.

Crear una solución segura de acceso.

## Flujo

Desde la ficha de cliente:

1. Administrador selecciona habilitar portal.
2. Verifica el correo o contacto registrado.
3. Genera acceso.
4. Puede enviar por email.
5. También puede copiar el enlace manualmente.
6. El cliente abre el enlace.
7. Se valida el token.
8. Se crea una sesión o mecanismo de acceso seguro.
9. El cliente consulta solamente su información.

## Requisitos

- Tokens aleatorios.
- Almacenamiento mediante hash.
- Expiración.
- Revocación.
- Uso único para el enlace de acceso.
- Validación del cliente.
- Rate limiting.
- Auditoría.
- Prevención de enumeración.
- Protección contra brute force.

Preferir que el acceso quede vinculado a una cuenta de cliente y no a un enlace público permanente.

Si se utiliza una sesión autenticada, permitir acceso posterior sin tener que solicitar un nuevo enlace en cada visita.

## Acciones del cliente

Permitir únicamente:

- Consultar solicitudes.
- Consultar órdenes.
- Consultar turnos.
- Consultar presupuestos.
- Aprobar o rechazar presupuestos.
- Consultar pagos.
- Consultar información propia.

El cliente nunca puede consultar información de otros clientes.

No darle permisos administrativos.

## Link manual

El administrador debe poder copiar el enlace generado.

El link manual debe tener exactamente las mismas protecciones del enlace enviado por correo.

No guardar ni mostrar el token en logs.

No permitir que el frontend invente o genere tokens.

Primera versión:

## Flujo

1. Descargar plantilla de ejemplo.

4. Leer encabezados.
5. Permitir mapear columnas.
6. Mostrar vista previa.

## Validaciones

- Teléfono.
- Email.
- Campos obligatorios.
- Tamaños.
- Duplicados.
- Caracteres inválidos.
- Cantidad máxima de registros.
- Direcciones.
- Relaciones.

La carga debe ser transaccional o utilizar un esquema de importación controlado que permita identificar claramente los registros aceptados y rechazados.
